# راهنمای نصب و ارتقای نود

این راهنما مال نود است (spec بخش 4.2 و 7.1، ردیف‌های T-545 و T-354). متن شل و مسیرها
انگلیسی می‌مانند.

## ترتیب استقرار (T-545)

1. **اول نودها، بعد پنل.** نسخه‌ای از پنل که جدول جفتی یا ورودی لاگ تازه‌ای امضا می‌کند
   که نود قدیمی نمی‌پذیرد، نباید پیش از نودها بالا بیاید.
2. نود را فقط وقتی ارتقا بدهید یا عمدا راه‌اندازی دوباره کنید که پنل در دسترس است. نود بدون
   پنل جواب می‌دهد (آخرین image و Plain DNS)، ولی تا پنل برنگردد نه گواهی تمدید می‌شود
   و نه فرمان تازه‌ای می‌رسد.
3. یک نود در هر لحظه. بعد از هر نود صبر کنید تا صفحه نود در پنل `applied_seq` تازه و
   «متصل» را نشان بدهد، بعد سراغ نود بعدی بروید. نودی که جفتش در حال drain است را ارتقا
   ندهید (صفحه نود «drain done» را نشان می‌دهد).

## نصب نود تازه

1. در صفحه ادمین یک ثبت‌نام بسازید (TOTP تازه). دستور نصب فقط یک بار نشان داده می‌شود و
   با یک فاصله شروع می‌شود تا در تاریخچه شل نماند. اعتبار توکن 15 دقیقه است.
2. دستور را روی میزبان **Ubuntu 24.04** و با `sudo` بزنید. توکن فقط از stdin می‌آید و در
   هیچ آرگومان یا لاگی نیست. اسکریپت پیش از هر تغییر نسخه سیستم را می‌سنجد؛ روی 22.04،
   26.04 یا هر چیز دیگر رد می‌کند و هیچ چیزی را عوض نمی‌کند.
3. اسکریپت زیر pin کلید پنل `root.json` را می‌گیرد و hash آن را با `--root` مقایسه می‌کند،
   بعد `node_ca.pem`، `ctrlz-verify` و bundle را می‌گیرد. `ctrlz-verify` امضا را با grant
   `bundle` همان root و همه فایل‌ها را با manifest می‌سنجد. فقط بعد از آن چیزی نصب می‌شود.
4. بعد از نصب، `journalctl -u ctrlz-agent` اثرانگشت کلید و چهار نشانی را نشان می‌دهد.
   آن‌ها را **کلمه به کلمه** با صفحه ادمین مقایسه کنید، بعد تایید اثرانگشت و تایید نود
   (هر دو با TOTP تازه).
5. اگر agent دوباره راه‌اندازی شود، همان ثبت‌نام را ادامه می‌دهد؛ کلید تازه نمی‌سازد و
   توکن نمی‌خواهد. اگر ثبت‌نام رد یا منقضی شد، یک ثبت‌نام و دستور تازه بسازید.

## ارتقا

نود فقط bundle را با `FetchBundle` در `/var/lib/ctrlz/bundles/node/<version>/` می‌گذارد و
می‌سنجد؛ حق نصب ندارد. نصب کار شماست:

```sh
ls /var/lib/ctrlz/bundles/node/                 # نسخه دانلودشده
cat /etc/ctrlz/versions/node                    # نسخه نصب‌شده
sudo ctrlz-node upgrade <version>
```

`upgrade` این‌ها را انجام می‌دهد: manifest را به پوشه root-only کپی می‌کند و با
`ctrlz-verify` ریشه‌ای (نه فایل‌های agent) و `/etc/ctrlz/root.json` می‌سنجد؛ نسخه‌ای که از
نسخه نصب‌شده بالاتر نباشد رد می‌شود؛ فقط فایل‌های فهرست manifest کپی می‌شوند (پیوند نمادین
یا فایلی که بزرگ‌تر از اندازه فهرست است رد می‌شود)؛ کپی دوباره با `ctrlz-verify` سنجیده
می‌شود؛ بعد `apply.sh upgrade` همان مراحل نصب را اجرا می‌کند و agent و dns و proxy را
راه‌اندازی دوباره می‌کند. هویت میزبان (کلیدها و `agent.conf`) دست نمی‌خورد.

ترتیب: حساب‌ها و بسته‌ها اول و با سرویس‌های روشن نصب می‌شوند (apt تا ۳۰۰ ثانیه منتظر قفل dpkg
می‌ماند؛ بسته‌ای که میزبان خودش نسخه‌ی جدیدتری از آن دارد دست نمی‌خورد و پایین‌ترسازی نمی‌شود)،
در این بازه هیچ سرویسی با بسته‌ها شروع نمی‌شود و `chrony.conf` گره از قبل جاگذاری شده است. فقط
بعد از آن سه سرویس متوقف می‌شوند. اگر هر مرحله‌ی بعدی شکست بخورد، همان سرویس‌هایی که روشن بودند
دوباره روشن می‌شوند و نسخه‌ی ثبت‌شده عوض نمی‌شود.

بعد از ارتقا:

```sh
systemctl is-active ctrlz-agent ctrlz-dns ctrlz-proxy
cat /etc/ctrlz/versions/node
```

کد خروج `ctrlz-verify` می‌گوید کدام بررسی رد شد (پیام فقط نام بررسی را می‌گوید، نه محتوا):
`10` root (ناخوانا، ناسالم، منقضی یا کلید آزمایشگاهی در باینری غیرآزمایشگاهی)، `11` امضا یا grant،
`12` تازگی یا نسخه، `13` فایل (ناموجود، اندازه، hash، فایل خارج از فهرست یا غیرعادی).

بازگشت به نسخه قدیمی‌تر پذیرفته نمی‌شود (ضد rollback). برای برگرداندن، همان کد قدیمی را
با شماره نسخه بالاتر دوباره بسازید و امضا کنید.

## فایل‌ها و حساب‌ها

| مسیر | مالک | نکته |
|---|---|---|
| `/usr/local/bin/ctrlz-node`, `/usr/local/sbin/ctrlz-verify` | root | agent نمی‌تواند عوضشان کند |
| `/etc/ctrlz/root.json`, `/etc/ctrlz/versions/node` | root | upgrade فقط از این‌ها می‌خواند |
| `/etc/ctrlz/agent.conf` | root | `hub` و چهار نشانی |
| `/var/lib/ctrlz/` | `ctrlz-agent:ctrlz` | `keys/` فقط agent، `bundles/` فقط agent |
| `/etc/ctrlz/unbound`، `/etc/ctrlz/chrony` | agent | تنها مسیرهای قابل نوشتن بیرون از `/var/lib/ctrlz` |

گروه `ctrlz` فقط `ctrlz-dns` و `ctrlz-agent` را دارد. `ctrlz-proxy` و دو کاربر Unbound گروه
خودشان را دارند. agent با polkit فقط start و stop و restart برای `ctrlz-dns`،
`ctrlz-unbound`، `ctrlz-unbound-free` و `chrony` را دارد.

دو Unbound را `systemctl enable` نکنید: agent بعد از سنجش‌هایش (core dump، کف نسخه، تنظیمات
ثابت) روشنشان می‌کند و خودش دوباره راه‌اندازی می‌کند.
